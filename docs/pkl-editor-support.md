# What the editor offers

What pkl-lsp answers on `/edit` about code written against `@fh-dashboard`: completion, hover,
go-to-definition and errors flagged before the build. Use it when shaping the library: a shape
the editor follows is one an author can discover without the docs, and a gap is a cost the shape
has to be worth.

`PklEditorSupportSuite` asks each case below, at the cursor `‸`, through `LspBridge.session`
as the page's `@codemirror/lsp-client` connects, in a workspace the backend has prepared
(bootstrapped, a dump seeded, built once). It renders this table. A gap that starts working
fails the suite too, so the table cannot lag in either direction. Each case's source also goes
through the dashboard build, so no case asks about code the build refuses.

pkl-lsp resolves `@fh-dashboard` and `@fh-home` only through a project it has loaded, and the
add-on ships no `pkl` CLI for its own sync to run. So the backend provides what a sync would:

- **the project state:** every build writes `<workspace>/.pkl-lsp/projects.json` beside the
  lockfile, from what pkl-core resolved (`PklLspProject`);
- **the cache:** pkl-lsp reads packages only from `$XDG_CACHE_HOME/pkl`, never the project's
  `moduleCacheDir`, so the build keeps `pkl-lsp-xdg/pkl` beside the cache as a link to it, and
  the bridge starts pkl-lsp with `XDG_CACHE_HOME` there;
- **the workspace folder:** pkl-lsp loads a project only for a client that declares one, which
  `@codemirror/lsp-client` does not, so the bridge adds the workspace to `initialize`.

The state file is pkl-lsp's format, not pkl-core's: a pkl-lsp bump that moves it fails every
case at once.
