# What the editor offers

What pkl-lsp answers about code written against `@fh-dashboard`: completion, hover,
go-to-definition and errors flagged before the build. Use it when shaping the library: a shape
the editor follows is one an author can discover without the docs, and a gap is a cost the shape
has to be worth.

`PklEditorSupportSuite` asks pkl-lsp each case below, at the cursor `‸`, in a bootstrapped
workspace, and renders this table. A gap that starts working fails the suite too, so the table
cannot lag in either direction. Each case's source also goes through the dashboard build, so no
case asks about code the build refuses.

Two clients, because what makes pkl-lsp work is the handshake:

- **A desktop editor** (VS Code, Neovim, with the Pkl extension) declares workspace folders,
  answers `workspace/configuration` with a `pkl` CLI 0.33+, and asks `pkl/syncProjects`. pkl-lsp
  then resolves the package imports through that CLI.
- **`/edit`**, the add-on's page, connects as `@codemirror/lsp-client` does: no root, no workspace
  folders, configuration unanswered, no sync, and the image ships no `pkl` CLI. pkl-lsp then
  answers nothing at all, not even a diagnostic.

Go-to-definition into the package lands on a `pkl-lsp://jar/…` uri, a virtual document only a
client that asks pkl-lsp for its contents can open.

The module every case is pasted into imports `@fh-dashboard/components.pkl` as `c`,
`query.pkl` as `q`, the dump as `dump`, and names `local light` a dump light. Locally the suite
needs a `pkl` 0.33+ on the sbt server's PATH, or its desktop cases are skipped; CI installs one.
